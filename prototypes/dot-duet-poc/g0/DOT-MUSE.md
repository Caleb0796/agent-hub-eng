## 如何验证中转不可读

1. 两端实际核验同一份端点源码的 SHA-256，并在主人明确批准后执行。Dot 复用自己的密钥；Muse 在自己的专用目录生成密钥，原生回复确认私钥文件权限为 0600，未上传。
2. 两端公钥指纹经各自原生回复独立核对，再在本机控制台完成工程认领。Muse 固定 Dot 公钥；Dot 在主人针对具体 Muse 指纹确认后固定该公钥。
3. Dot 在自己的运行环境生成高熵随机正文，先加密再调用 Hub。发送时不公布正文或正文摘要。Muse 只能从实际收到的密文解密后计算挑战摘要，再加密回复。
4. Dot 用自己保存的原挑战独立核对回应中的摘要。双方完整正文摘要交叉相符，消息 ID、回复关系与中转记录一致。
5. 本地验收脚本仅使用中转快照、公钥和原生摘要回执，验证两个 Ed25519 签名；使用无关 age 身份尝试解密两条密文，均被拒绝。脚本没有取得任何端点私钥。
6. 新中转状态及该轮通道日志中没有正文标记、`AGE-SECRET-KEY-` 或端点私钥字段。扫描仅是辅助证据，结论同时依赖端点代码、密钥位置、实际解密回执和密码实现。

Hub 持有的连接凭证用于认证、限定调用身份；它们不是正文解密密钥。原生模型服务商与各自运行环境仍在信任边界内。若中转方同时控制端点或未经核验的客户端更新，本轮结论不能直接延伸到那种情形。

## 保留的格式问题

Muse 的回应在 `ACK:` 后多了一个 ASCII 空格。Dot 最初用严格正则匹配，把“格式不符”也记录为 `ack_matches_local_challenge=false`。初始失败回执和验收错误已保留。

Dot 随后仅在本地使用原有密文的历史阅读模式重新诊断，不修改或补发消息。最终分别确认：

- `ack_matches_local_challenge=true`：提取出的 64 位摘要与本地原挑战摘要相同。
- `strict_ack_format_valid=false`：原消息仍不符合无空格的严格格式。
- `ack_leading_ascii_spaces=1`，`ack_trailing_ascii_spaces=0`。

因此本轮加密传输和摘要一致性通过，应用层严格 ACK 格式检查仍失败。后续应使用确定的结构化回执格式，避免让自由文本排版承担协议语义；本次没有修改已传输内容来“修复”验收。

- Muse 原生实测：Python 3.12.3、Node 24.22.1；专用目录由独立进程成功读回；隔离 venv 导入 `pyrage==1.4.0`、`cryptography==50.0.2` 成功。
- Muse 使用原生 Secure Vault 保存专用 API key。认证材料没有进入聊天、脚本、命令参数或日志；调用沿用原生代理和审批。
- 初始 MCP 客户端混用了 2026-07-28 标头与旧式 initialize。改用旧式多请求握手后仍遇到审批等待；服务端确实收到过认证初始化，不能把客户端超时解读为“请求从未到达”。
- 最终使用服务已支持的 2026-07-28 单请求 tools/call 模式。Muse 返回 HTTP 200，实际确认 role=muse、peer=dot 与本轮 run_id；随后原生注册、收信和发信成功。
- 原生界面出现独立的 CONNECT 和 POST 审批。后续在新一轮准备时，审批历史显示上一轮主机存在一条 `Site always allowed` 记录；因此此前“未授予永久站点放行”的表述不准确，现予更正。现有记录不足以确定该选择来自哪次具体界面操作；临时通道已按记录关闭。
- Dot 对新代码执行和持久公钥互信分别要求主人操作时确认；这些确认都已取得。此轮仍是工程辅助接入，不是“一句话冷启动、零配置”的用户体验验收。
- 本机认领由助手代操作，验证状态机和界面；不代替生产 Owner 登录认证、人类在场证明或两名独立 Owner 的试点。
